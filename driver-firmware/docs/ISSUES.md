# Fault History

Every defect found in this project, what it looked like, what caused it,
and how it was resolved. Entries are ordered roughly by when they were
found. Several were misdiagnosed before being resolved correctly; those
attempts are recorded because the reasoning that failed is often more
useful than the fix that worked.

Read this before changing the capture path. Most of the obvious
simplifications here have already been tried and have already failed for
reasons that are not obvious.

---

## 1. Serial port not readable

**Symptom.** No output from the device on any terminal.

**Cause.** Board target mismatch. The project was building for `pico`
(RP2040) while the hardware is a Pico 2 (RP2350).

**Fix.** Corrected `board` to `rpipico2` in `platformio.ini`.

---

## 2. Boot output missed

**Symptom.** Startup diagnostics never seen, because firmware cannot be
uploaded while a serial monitor holds the port, and by the time a monitor
is opened the boot sequence has already scrolled past.

**Fix.** `setup()` blocks on `while (!Serial)` before printing anything.
USB CDC reports not-ready until the host asserts DTR, so the device waits
for a monitor rather than racing it.

---

## 3. Wrong SCLK pin

**Symptom.** No ADC response.

**Cause.** The pin comment said physical pin 14 but the constant held
GPIO 12. GPIO 10 is physical pin 14.

**Fix.** Corrected the constant. The comment was right and the code was
wrong, which is why this survived several readings.

---

## 4. ADC returning a fixed value

**Symptom.** Every conversion read back identical regardless of input.

**Cause.** SDI was tied low, which sends command `0000b` on every
transaction. That command is not documented for this part.

**Fix.** SDI held high, which is command `1111b`, the datasheet's
"default mode": *"A default mode command can be achieved by simply tying
SDI to +VBD."*

---

## 5. Every pixel reading full scale

**Symptom.** All conversions returned `0x3FFF`.

**Cause.** The CFR reset bit D0 does not self-clear. Writing it low left
the converter permanently in reset, and full scale is the documented
output in that state. The reset artifact was being observed continuously
rather than once.

**Fix.** `resetAdcConfig()` performs two writes: D0 low to force a known
state, then D0 high to return to normal operation.

---

## 6. Pixel count wrong (1078 instead of 1024)

**Symptom.** More trigger pulses counted per frame than the sensor has
elements.

**Initial misdiagnosis.** Attributed to sensor dummy pixels, and
"resolved" by capping the count at 1024. This was rejected: capping hides
a miscount rather than correcting it, and leaves the extra edges free to
displace real pixels.

**Cause.** Contact bounce on the trigger line. Measurement showed a
companion glitch 1 to 2 microseconds after each genuine edge.

**Fix.** An `ARMED` / `REFRACTORY` state machine with a 16 microsecond
blackout window, sized against the measured bounce and the 20 microsecond
pixel period. See issues 12 through 15 for where this ended up.

---

## 7. Slow sliding artifact on a static scene

**Symptom.** A flat, saturated scene showed a slow horizontal drift.

**Initial misdiagnosis.** Mains hum. The arithmetic was suggestive: 50 Hz
against 48 fps predicts a 2 Hz beat, close to what was observed. It was
wrong.

**Cause.** SCLK was generated by a free-running PWM whose phase relative
to the CPLD's independent trigger clock drifted continuously, because the
two clocks are separate oscillators with no synchronisation.

**Fix.** SCLK is bit-banged on demand for each transfer. Every read now
has identical, self-contained timing regardless of when in absolute time
it begins.

---

## 8. Severe pixel loss after the bit-bang change

**Symptom.** 690 of 1024 pixels captured, with a clean cutoff.

**Cause.** The inter-edge delay used `for (volatile int i = 0; ...)`. A
volatile loop counter forces a memory round trip every iteration, so the
real duration was far longer than the intended NOP count and each
transfer overran its budget.

**Fix.** Replaced with a fixed, unrolled run of NOPs. A straight-line
sequence has a known cycle count; a volatile-controlled loop does not.
`maxread` was added at the same time to measure transfer duration rather
than assume it.

---

## 9. Frame timing coupled to unrelated host activity

**Symptom.** The live view visibly disturbed by clicking the host's
trackpad or by having several windows open.

**Cause.** `runFrame()` issued a blocking 4 KB `Serial.write()` before
firing the START pulse. When the host was slow to drain the USB endpoint,
the write blocked, which delayed START, which perturbed frame timing.
Host activity unrelated to the instrument was therefore visible in the
data.

**Fix.** Frame text is composed into a staging buffer, which is bounded
CPU work, and START fires immediately afterwards. Bytes drain through
`pumpTx()`, gated on `Serial.availableForWrite()` so it never blocks. If
the host falls behind, that frame's text is dropped rather than delaying
acquisition, and the drop is counted as `txdrop`.

---

## 10. Cascading corruption after an abandoned scan

**Symptom.** One short frame followed by several more.

**Cause.** When the scan watchdog fired, the CPLD had no way to know and
continued emitting triggers for the remainder of that scan. The PIO state
machine queued them. The next frame then popped those stale entries as if
they were its own first pixels.

**Fix.** Both state machine FIFOs are cleared immediately before each
START pulse.

---

## 11. Stale data in short frames

**Symptom.** A genuinely static scene appeared to flicker.

**Cause.** With double buffering, slots not written during a short frame
still held data from two frames earlier. Old and new pixels were being
mixed within one frame with nothing to distinguish them.

**Fix.** Initially a zero fill, later replaced by the `MISSING_PIXEL`
sentinel (issue 16), because zero is a legal reading and therefore
ambiguous.

---

## 12. Interrupt-based edge detection loses pixels

**Symptom.** Frames intermittently short, with no rejected edges counted.

**Cause.** The RP2350 latches a pending GPIO interrupt as a single sticky
bit per pin per edge type, not as a counter. Two edges closer together
than interrupt service latency coalesce into one entry. The pixel
disappears with no trace in any software counter, because there is
nothing to reject: the handler simply never runs a second time.

**Fix.** Superseded by issues 13 and 14.

---

## 13. CPU polling is worse than interrupts

**Symptom.** Replacing the interrupt with a tight polling loop made pixel
loss substantially worse.

**Cause.** Removing the pixel-trigger interrupt does not stop other
interrupts. USB activity in particular preempts the polling loop
regularly. Unlike an edge latch, a level read has no memory of a
transition that occurred entirely during a preemption, so a narrow pulse
inside that window is lost with no trace at all. This requires only one
badly timed preemption, where coalescing requires two edges to collide.

**Note.** This approach was adopted from a sibling project where it works
correctly. There the polled signal is generated by the same chip's own
PIO block and nothing else needs to preempt observation of it. The
technique did not transfer.

**Fix.** Superseded by issue 14.

---

## 14. Trigger detection moved into PIO

**Fix.** `pixel_trig.pio` implements the same `ARMED` / `REFRACTORY`
policy in a PIO state machine. It cannot be preempted by ARM-core
interrupts, and it reports confirmed triggers through a FIFO of depth 8
rather than a single bit, so a brief CPU stall is absorbed instead of
causing loss.

---

## 15. PIO program stalls mid-scan

**Symptom.** Isolated frames dropping from 1024 pixels to roughly 800,
with normal operation resuming on the following frame.

**Cause.** The first version of the PIO program waited unbounded for the
trigger line to return high before re-arming. That is correct when the
line does return high promptly. When it did not, for any reason, the
state machine blocked there for the remainder of the scan.

**Fix.** The wait is bounded. The state machine re-arms regardless after
a fixed number of cycles. The worst case becomes one possible spurious
double count rather than a scan-ending stall.

---

## 16. Missing pixels indistinguishable from dark readings

**Cause.** Short frames were zero filled, and zero is a legal reading.

**Fix.** `MISSING_PIXEL` (`0xFFFF`), deliberately outside the 14-bit code
range so a real conversion cannot produce it. The host renders these
distinctly and excludes them from statistics rather than averaging them
in as zero.

---

## 17. PIO sampling rate throttled to 1 MHz

**Symptom.** Steady pixel loss that survived issues 14 and 15.

**Cause.** The PIO state machine's clock divider was set so one cycle
equalled one microsecond, chosen only so `REFRACTORY_US` could be pushed
in as a cycle count without conversion. A PIO `wait` samples its pin once
per cycle, so the divider is the edge-detection sampling rate. The state
machine was observing the trigger at 1 MHz and was blind between samples.

This is the same class of defect as issue 13, reintroduced by a different
route: moving observation off the ARM core prevents preemption, but
throttling the observer to 1 MHz restores the blind windows.

**Fix.** Divider set to 1.0, full system clock, roughly 6.7 ns per sample.
The refractory window is now counted in cycles, converted at runtime from
`REFRACTORY_US` so it remains the single source of truth in wall-clock
terms.

---

## 18. Image drift caused by arrival-order indexing

**Symptom.** The image slid sideways over time.

**Cause.** Pixels were stored in arrival order. One lost pixel shifted
every subsequent pixel in that frame one slot earlier. The frame remained
internally plausible, with no gap and no marker, but its entire tail was
spatially wrong by an amount that varied with where and how often loss
occurred.

**Fix.** Positional indexing. A pixel's slot is derived from when its
trigger arrived, not from how many have been counted:
`steps = round(gap / period)`. Loss becomes a marked hole at its own
position rather than a global shift.

---

## 19. Loss detection fabricating the drift it prevented

**Symptom.** Frames arriving at exactly half length, `pulses 513`,
`miss 511`, `dur 10273us`, in exactly half the normal scan time.

**Cause.** The pixel period was estimated from the **minimum** observed
gap, on the reasoning that a missed pixel can only make a gap larger. That
ignores measurement jitter in the other direction. Timestamps are taken
when the CPU pops the FIFO, and `readAdcSample()` blocks with interrupts
disabled, so a trigger arriving mid-read is observed late and the next one
appears artificially close. Measured gaps spanned 13 to 26 microseconds
against a true period of 20.0.

With the estimate at 13, an ordinary 20 microsecond gap exceeded the
1.5x loss threshold and scored two steps, so every pixel advanced two
slots and the scan filled with holes the firmware had invented.

**Fix.** The **median** of trustworthy gaps, from a 64-bucket histogram.
The median is robust to jitter in both directions and remains correct with
a substantial fraction of genuine holes present. Cross-check: frame
duration divided by pixel count gave 20.01 microseconds on every frame,
matching the median and not the minimum.

Two further guards keep bad samples out of the estimator: only gaps that
scored exactly one step contribute, and only gaps observed while genuinely
idle-waiting contribute. FIFO level alone cannot distinguish a fresh
arrival from one that queued during a blocked read.

## 20. Scans that never begin

**Symptom.** Isolated frames with `pulses 0`, `raw 0`, `fifo 0`, and
`dur` exactly equal to the watchdog period. The following frame ran
roughly 34 milliseconds late.

**Cause.** The CPLD occasionally does not act on a START pulse, at
roughly one frame in several hundred. `raw 0` is conclusive: the
unfiltered diagnostic state machine saw no transitions at all, so nothing
was emitted, as distinct from something being emitted and filtered.

The 100 millisecond whole-scan watchdog was the wrong instrument. The
frame was lost and the schedule was disrupted well beyond the original
fault.

**Fix.** `FIRST_TRIGGER_TIMEOUT_US`, 2 milliseconds, bounds the first
trigger specifically. On timeout, `runFrame()` clears both FIFOs and
issues another START, up to three retries. Re-issuing is safe because the
CPLD demonstrably did nothing with the previous pulse.

**Result.** Two START-ignored events in 1053 frames, both recovered on the
first retry, each producing a complete frame. Maximum frame lateness fell
from 33762 to 2 microseconds.

---

## 21. Pixel values corrupted by single-bit shifts

**Symptom.** Isolated pixels at exactly twice or exactly half their true
value.

**Misdiagnosis.** The spike classifier reported "analog: settling, droop
or noise". It tested for bit **flips**, which change a value by a fixed
power of two. A **shift** scales the value, so the difference equals the
signal itself and is not a power of two. Shifts fell through to the
residual category. This would have sent the investigation to the analog
front end for a digital fault.

**Cause.** `0x17A5` read as `0x2F4A`, `0x17AA` read as `0x0BD5`. Exact
single-bit shifts, with every implied true value in the normal range. The
firmware clocks exactly 16 bits, so the extra clock is not ours: a
spurious edge was being induced on SCLK, most likely by the CS transition
coupling into it.

Measured at 0.2930 percent of pixels, almost entirely left shifts.

**Attempts that failed, with measurements:**

| Change | Result |
|---|---|
| CS setup 27 ns to 1 or 2 us | no reduction; `maxread` reached 55 us, pixels lost |
| SCLK approx 18 MHz to 2.5 MHz | 1.33 to 1.03 percent, within noise; broke timing budget |
| `gpio_put` to direct SIO registers | worst-case read 11 us to 10 us only |
| Low-bit invariant plus re-read | catches nothing: a left shift pulls in a zero, so the low bits stay clean |

An earlier conclusion that longer CS setup helped came from one to three
events on a single monitored pixel and did not survive full-frame
measurement.

**Fix.** Two changes, together:

1. The read path moved into RAM with `__not_in_flash_func`. Execution
   from flash via the XIP cache introduces variable instruction-fetch
   stalls, which made the bit-bang timing non-deterministic at the CS and
   SCLK boundary. Worst-case read fell from 10 to 6 microseconds.
2. Double read with median-of-three tie-break, affordable only because of
   the first change. The same conversion is read twice; the ADS7279 holds
   the result on DOUT until the next conversion, so the second read is a
   genuine repeat measurement rather than a new sample.

**Result.** Zero shifts, zero flips, zero outliers across 695,296 pixels,
from 1809.

**Caveat.** The double read reported zero disagreements. If shifts were
still occurring at 0.29 percent per read, roughly 4000 disagreements would
be expected. Zero means the reads were already clean, so the RAM placement
is what carries the fix and the double read is insurance. The two changes
are confounded in that measurement. Reverting the double read would
reclaim about 6 microseconds of per-pixel budget if that becomes
necessary.

## 22. `maxread` misinterpreted

**Symptom.** Worst-case read times of 30 to 55 microseconds against a 20
microsecond budget, which appeared to indicate an extremely slow transfer.

**Cause.** `maxread` is measured with `micros()` outside the
interrupts-disabled section, so it includes any preemption that occurs
around the critical section. USB interrupt service dominates the maximum.
The minimum, not the maximum, is the transfer time.

**Consequence.** Several conclusions drawn from `maxread` maxima during
issue 21 were unsound. The minimum was the correct figure throughout.

---

## 23. Configuration register readback unreliable

**Symptom.** `resetAdcConfig()` reads back `0xFFC` on one boot and `0x100`
on another, against an expected `0xFFD`, with identical firmware and a
clean conversion stream both times.

**Assessment.** A register that reads back inconsistently while the device
operates correctly indicates the readback path is unreliable, not that the
register holds an unexpected value. Consistent with the level shifter
limitation on the SDI path: separate testing showed CFR readback stable at
200 kHz and random at 2 MHz.

**Status.** Open, and not blocking. Per-pixel reads use default mode with
SDI held high and never consult the CFR. The practical consequence is that
the boot-time CFR lines are not a trustworthy diagnostic and should not be
used to infer chip state.

---

## 24. `early` counter saturated

**Symptom.** The early-deassertion counter fires on essentially every
read, 945,151 of 945,152 in one capture.

**Assessment.** The trigger pulse is simply shorter than the roughly 6
microsecond transfer, as a constant condition rather than an intermittent
fault. This is benign: the ADS7279 holds the result on DOUT until the next
conversion begins, so a read that outlives the pulse still returns valid
data.

The original hypothesis, that a SAR conversion read too early would bias
toward full scale, is not supported. Saturation at 100 percent alongside
clean, stable pixel values is inconsistent with the reads being corrupted.

**Status.** The counter has no discriminating power as written. Its
remaining use is inverted: a value that ever drops well below the pixel
count would indicate the pulse width changed.

---

## 25. Generated PIO header can go stale silently

**Symptom.** None, which is the problem.

**Cause.** `pixel_trig.pio.h` is generated by `pioasm` and checked in.
PlatformIO's Arduino builder has no equivalent of the Pico SDK's
`pico_generate_pio_header()`, so the header was regenerated by hand.
Editing the `.pio` source and forgetting that step produces firmware that
compiles, links, flashes and runs while containing the previous program.
Nothing in the build output indicates this. A sibling project lost
significant time to exactly this, evaluating timing theories against a
binary that never contained the edits under test.

**Fix.** Two independent protections:

1. `tools/build_pio.py`, registered as a pre-build action, regenerates any
   header whose source is newer. A syntax error fails the build rather
   than leaving the old header in place.
2. `printPioBuildStamp()` prints, at boot, a checksum computed over the
   PIO instruction words actually linked into the running binary.

The second exists because the first proves only what the build system
intended. If the source changes and the boot checksum does not, the
running firmware does not contain the change.

## 26. Device identification field truncated

**Symptom.** The host application parsed the firmware build date as
`Aug`.

**Cause.** `__DATE__` expands to `Mmm dd yyyy`, with spaces. The `I` line
is space-separated `key=value` pairs, so the value ended at the first
space.

**Fix.** Spaces are replaced with underscores before the field is emitted.
Values in that line must not contain spaces.

---

## 27. Transmission limited the frame rate

**Symptom.** Requested frame rates above 25 Hz were not achieved. The
ceiling was about 30 fps against a sensor limit of 48.8 Hz, and above it
the host fell behind badly enough to lose pixels: 15 per second at a
requested 40 Hz.

**Cause.** Frames were sent as hex ASCII, two characters per data byte.
A frame cost 4111 bytes plus a 250 byte status line, which is 209 KB/s at
48 Hz.

**Fix.** Binary frame format, protocol 2: magic, sequence, captured count,
pixel count, `uint16` data, checksum. 2062 bytes per frame, 111 KB/s at
48 Hz.

Because frames are now binary, the host reader cannot work line by line;
payload bytes contain newlines at arbitrary positions. It scans for the
magic, treats preceding bytes as text, and validates both the pixel count
and the checksum before accepting a frame, which also allows
resynchronisation after a dropped byte.

**Result.** 40 Hz with zero drops, zero missing pixels and zero checksum
errors. Above 44 Hz the frame period approaches the 20.5 ms scan and
pixels are missed again, so 40 Hz is the clean ceiling and the scan is now
the binding constraint.

---

## 28. Command replies interleaved into frames

**Symptom.** The `id` command returned nothing. Raw capture showed frame
payload appearing as its own line and a status line truncated mid-field.

**Cause.** Command replies used `Serial.println()` directly while frame
data was metered out by `pumpTx()` from a separate buffer. Two independent
writers on one stream. A reply emitted mid-frame was inserted into the
middle of the frame, destroying both.

**Fix.** See issue 29; the first attempt was wrong.

---

## 29. Command handling suppressed itself into a deadlock

**Symptom.** The device stopped responding to commands entirely and could
not be recovered without reflashing. It ran at a fixed 47.7 fps regardless
of any requested rate.

**Cause.** The first fix for issue 28 suppressed command handling whenever
the transmit buffer held data. That prevented interleaving, but commands
are polled from `loop()`, which runs immediately after `runFrame()` has
just staged a frame. With frames running back to back the buffer was never
observed empty at that moment, so commands were never processed. Setting
the free-running rate made the condition permanent.

This was a worse fault than the one it fixed: interleaving corrupted
occasional messages, whereas this made the device uncommandable.

**Fix.** A single output queue with atomic appends. Frames, status lines
and command replies all append to it, and `pumpTx()` is the only writer to
the port. A message is either appended whole or rejected whole, so partial
messages cannot exist and no gating on transmit state is required.

**Lesson.** Scheduling around a shared resource is fragile. Removing the
sharing is not.

---

## 30. Text lines fragmented by the binary reader

**Symptom.** Command replies arrived split, for example `A rate_hz=` in
one message and `22` in another, with single characters appearing as
separate messages.

**Cause.** The protocol 2 reader dispatched whatever text bytes had
arrived between frames, rather than waiting for a complete line. Serial
reads split lines at arbitrary positions.

**Fix.** Text is accumulated and only complete newline-terminated lines
are dispatched, with the remainder carried to the next read. Verified with
deliberately small read chunks.

---

## 31. Most of the noise floor was one 17.68 kHz interferer

**Symptom.** Two symptoms, eventually shown to be the same fault. Zooming
into the trace showed a small regular oscillation of a few pixels' period
riding on every spectrum. Separately, each pixel's value distribution came
out flat topped rather than Gaussian, with excess kurtosis near -1.3 on
every pixel checked across the array. Frame to frame noise sat at about
6.0 mV, 40 codes, independent of frame rate.

**Investigation.** Several hypotheses were tested and rejected against
measurement before the cause was found:

| Hypothesis | Test | Result |
|---|---|---|
| Ordinary Gaussian readout noise | Excess kurtosis | Rejected. -1.3 at 4 to 5 standard errors from 0 |
| Slow drift over the capture | Detrend, recompute kurtosis | Rejected. -1.30 becomes -1.31 |
| Periodic interference, frame to frame | Temporal FFT and lag autocorrelation | No line, no correlation. Misleading, see below |
| Common mode supply or reference disturbance | Correlate each pixel against a 128 pixel per-frame average | Rejected. r = 0.02 to 0.17, against 0.999 for a synthetic common mode case |
| Video line settling race | Correlate state against the step from the preceding pixel | Rejected. r weakly negative |
| Digital shift fault (issue 21) | Firmware `retry` and `reread` counters | Rejected. Zero over every capture. The double read agrees, so the value is already wrong before the transfer |
| Quantisation or a stuck bit | Distribution of raw code values | Rejected. All codes present, gaps of 1, no structure |
| Pico onboard regulator in PFM mode | Force PWM via GPIO23, A/B twice in one session | Rejected. 17.68 kHz and 46 codes in both states |

**Cause.** A single additive sinusoidal component on the analog video
signal at 0.3539 cycles per pixel, a period of 2.825 pixels, which at the
20 microsecond pixel period is 17.68 kHz. It accounts for about three
quarters of the noise variance.

The temporal tests were looking on the wrong axis. Pixels are read
sequentially at 20 microseconds each, so the readout samples at 50 kHz
while frames sample at 20 Hz. A 17.68 kHz component is far above the frame
rate and aliases into apparent randomness frame to frame, which is why the
temporal FFT and autocorrelation showed nothing. Along the pixel axis it
is directly visible and unmistakable: spatial autocorrelation reaches
+0.89 and -0.89 at small lags.

50 kHz / 17.68 kHz = 2.825, not an integer, so the interferer is
asynchronous to the readout and its phase is uniformly random from frame
to frame (circular resultant 0.0155 over 399 frames). A sinusoid sampled
at random phase is arcsine distributed, excess kurtosis -1.5, which is
exactly the flat topped shape observed. The two symptoms were one cause.

Confirmed additive rather than gain or reference related: amplitude held
at 54.0 to 54.2 codes across windows whose signal level ran from 2780 down
to 2345 codes. Frequency is stable to 0.1 percent across captures at
different frame rates.

**Fix.** `processing.notch_pattern()`, notching that band in the spatial
frequency domain, on by default and shown as a labelled control. Measured
on live hardware through the application's own path: interior noise 6.043
to 1.321 mV, a factor of 4.57, per pixel excess kurtosis -1.25 to +0.01,
and no pixel made worse anywhere on the array.

This is safe because interference and signal do not overlap in spatial
frequency. 99.96 percent of a real frame's energy lies below 0.30 cycles
per pixel, since emission lines span several pixels and the illumination
envelope spans hundreds, while the interferer is a spike at 0.354.
Synthetic emission lines added to real frames retain 100 percent of their
area, and 98.7 percent of peak height at 3 pixel FWHM, 100 percent at 5
pixels and wider.

The outer 15 pixels at each end improve by 1.4 to 2.5 times rather than 5.
A frame is not periodic, so the interferer has an arbitrary phase
discontinuity at each end. Mirror padding was tried and made the edges
worse, since the reflected copy breaks the sinusoid's phase at the seam. A
per-frame least squares sinusoid fit was also tried and handles edges
better, 17 against 25 codes, but the interior worse, 11 against 8, because
the interference is a narrow band rather than one exact frequency.

**Not fixed at source.** The interferer is upstream of the Pico, on the
sensor or CPLD driver board, and was not identified. The Pico's own
regulator was ruled out. Identifying it needs an oscilloscope on the
analog supply and video line, which is the correct next step if the
underlying 1.3 mV floor matters. 17.68 kHz may itself be an alias: the
readout samples at 50 kHz, so a source at 32.3, 67.7 or 82.3 kHz would
appear at the same place, and the pixel period is not known precisely
enough to distinguish them.

## 32. The notch rang at the array ends

Introduced by the fix for 31 and reported from use, not caught in
testing.

**Symptom.** With the notch on, spatial oscillation increased over
roughly the first and last 40 pixels. Unlike noise, it did not diminish
with stacking.

**Diagnosis.** That it survived stacking was the whole diagnosis.
Anything random averages down as the square root of frame count, so a
component that persists is deterministic. Measured against a 399 frame
stack, the notch was contributing 23 mV peak at the ends and 0.46 mV rms
in the interior, against a corrected noise floor of 1.2 mV.

**Cause.** Pixels 0 and 1023 are not measurements. Pixel 0 sits 86 mV
above its neighbour and pixel 1023 sits 199 mV below. To a Fourier method
those are two large impulses, and removing a frequency band from an
impulse leaves a decaying oscillation running inward from it. Because
those impulses come from the fixed shape of the frame rather than from
the interferer's random phase, the oscillation is identical in every
frame and stacking cannot touch it.

The magnitude was predictable in hindsight: 199 mV times the notched
fraction of the spectrum, about 0.12, is 24 mV, against 23 mV measured.

A second, smaller contribution came from removing a least squares line
before the transform. The transform treats the frame as one period of a
periodic signal, so the level difference between the first and last
sample is a step at the wrap point. The illumination profile is curved,
so a straight line left tens of millivolts of mismatch.

**Fix.** Both handled inside `notch_pattern()`:

- The end pixels are excluded from the transform and returned unchanged.
  Done inside the function rather than by requiring callers to mask
  first, so the result cannot depend on the order corrections are applied
  in, and so unmasking the ends for inspection cannot silently
  reintroduce it. Verified identical output for notch alone, notch then
  mask, and mask then notch.
- The baseline is anchored to the median of the outermost usable pixels
  at each end instead of being a least squares line, which removes the
  wrap step.

Measured across six independent captures: surviving stacked artifact 23.2
to 0.57 mV, a factor of 41, with interior noise unchanged at 1.22 mV.
Ripple in the stacked frame at the ends is now at or below the interior
figure, where before it was the worst region on the array. Line fidelity
is unchanged: 100 percent of area, 98.7 percent of peak at 3 pixel FWHM.

**Rejected.** Narrowing the notch bands cut the artifact from 0.57 to
0.52 mV but raised interior noise from 1.22 to 1.38 mV. Mirror padding
made the edges worse, since the reflected copy breaks the sinusoid's
phase at the seam. Smoothed baselines of width 9, 15 and 31 gave no
improvement at all, which was the clue that the baseline was not the main
term and sent the investigation to the end pixels.

**Lesson.** Whether an artifact survives stacking separates deterministic
from random directly, and is worth checking on any correction that
touches the frequency domain. The residual edge error that remains, 0.57
mV, is the interferer's own phase discontinuity at the ends. That one is
random per frame and does average away, which is why it is acceptable
while the impulse artifact was not.

## 33. The pixel power spectrum was blind to what it was built to find

Three faults found in one debugging pass, live against hardware, while
building the Distribution tab's spectrum views (`APPLICATION.md` section
8.2, 8.3).

**Fault 1: the frequency axis visibly rescaled.** The per-frame
("vs time") spectrum re-read the live frame rate on every redraw to
compute its Nyquist limit. `self.fps` is a genuine measurement, refreshed
roughly once a second, and fluctuates by a percent or so; recomputing the
axis bounds from it every redraw made the whole plot rescale continuously
while streaming. Fixed by capturing the sample rate once when the history
starts accumulating (`self.hist_fs`) and holding it fixed until the
history is cleared, which already happens on reconnect and on any
exposure change. Confirmed live: `self.fps` measured 19.726 then 20.247
Hz within one test run; `self.hist_fs` and the plot's pixel geometry were
bit-for-bit identical before and after.

**Fault 2: the spatial spectrum found the wrong peak, then found no peak
at all.** Built to reach into the kHz range the same way the entry 31
investigation did: a 256-pixel window around the clicked pixel, FFT'd and
averaged over recent frames. First version subtracted only the window's
mean before transforming, not a baseline -- the same mistake entry 32 had
already been made and fixed for `notch_pattern()`, reintroduced here
because the two code paths were written separately. The illumination
profile is real and large even across a 256-pixel window, and a linear
detrend was not always enough: measured live, the reported "peak" was
consistently the lowest resolvable frequency (195 Hz, the width of the
window), not the interferer, on every pixel tried.

Endpoint-anchored baseline (matching `notch_pattern()`) narrowed but did
not eliminate this, so the peak *search* was restricted to 15 kHz and
above -- `notch_pattern()`'s own established boundary, where 99.96
percent of real spectral energy already sits below it. The full curve is
still drawn from its lowest bin; only the automatic marker is restricted.

That fix immediately exposed the third fault: with the search correctly
excluding real low-frequency content, the marked peak became 20.5 kHz at
under 1 mV amplitude, consistently, on every pixel -- not the 17.68 kHz,
8 mV interferer entry 31 had established beyond doubt.

**Fault 3: the view was reading already-corrected data.**
`processing.notch_pattern()` is applied in `_process()` before a frame is
pushed to `self.pixel_history`, and the notch is on by default. It
removes exactly the frequency band this view exists to display. A direct
comparison proved it: the same 60 frames, analysed by hand from the raw
serial stream, showed the interferer at 8.04 mV; read from
`self.pixel_history` inside the running application, the same window
showed it at noise-floor level, under 1 mV, because it had already been
filtered out one step earlier in the pipeline.

Fixed with a second buffer, `self.pixel_history_raw`, populated from
`processing.codes_to_volts()` alone -- no dark, flat, notch, or mask --
in parallel with the corrected one, and used exclusively by the
within-frame spectrum view. Confirmed live afterward: 17.578 kHz at 8.2
mV, on pixels 500, 128, and 900 alike, matching entry 31 to three
significant figures.

**Lesson.** A diagnostic view built to reveal a correction's effect must
not consume that correction's output; every other view in this
application legitimately shows the corrected, displayed data, which is
what made this easy to get wrong by consistency with the rest of the
file rather than by any one bad line. All three faults were found by
running the actual feature against live hardware rather than by
inspection: the rescaling was invisible in a static screenshot, the wrong
peak looked plausible until checked against the known 17.68 kHz answer,
and the empty spectrum only stood out because a value that should have
been 8 mV read as under 1.

## Recurring lessons

**Measure before concluding.** Issues 7, 19 and 21 were each first
attributed to a plausible mechanism that turned out to be wrong. In every
case the correct answer came from a measurement that distinguished the
hypotheses, not from further reasoning about them.

**Small event counts are not evidence.** The claim that longer CS setup
reduced shifts rested on one to three events and was reversed by
full-frame measurement.

**A diagnostic that tests the wrong hypothesis is worse than none.** The
spike classifier in issue 21 gave a confident and wrong answer because it
tested for flips when the fault was shifts.

**Techniques do not transfer without their preconditions.** CPU polling
(issue 13) works in a sibling project because the signal there is
generated by the same chip and nothing else competes for observation.

**Distinguish silent errors from marked ones.** Missing pixels are
acceptable when marked; wrong values that look plausible are not. Several
fixes deliberately trade a small increase in marked dropouts for a large
reduction in silent corruption.
